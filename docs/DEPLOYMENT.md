# Deployment Guide — step by step

How to deploy the `rs-*` plugin skills (and the orchestrated pipeline) to each surface. Follow the method you
want top to bottom. Paths assume you are in the repo root:
`/home/vishnu-pradeep/Desktop/data/projects/intuitiolabs/agents`.

| Method                           | What you get                                                 | Effort | Best for                                        |
| -------------------------------- | ------------------------------------------------------------ | ------ | ----------------------------------------------- |
| **1. Claude Code**         | All 4 skills + full orchestration, locally; renders D2       | Low    | Daily use, testing, the team's own machines     |
| **2. claude.ai**           | Skills available in the chat app; Notion connected           | Low    | Non-technical team members, one stage at a time |
| **3. platform.claude.com** | One hosted agent running the whole pipeline (Managed Agents) | High   | Productionized, button-triggered, server-side   |
| **4. Agent SDK runner**    | The pipeline as a script in your own process/server          | Medium | Automation without the hosted beta              |

Everything below uses the plugins already built in [`plugins/`](../plugins/) (generated from
[`src/plugins/`](../src/plugins/)) and the runners in [`orchestrator/`](../src/orchestrator/). The
pipeline chain uses `brd-generator`, `prd-generator`, `technical-design-generator` and
`estimation-generator`, all in `rs-scoping`. For the plugin catalogue and install commands see the
[README](../README.md#plugins); for releasing changes see [Updating a skill](#updating-a-skill).

## Fastest path — the Makefile

Every artifact in this guide is generated by a `make` target. Run `make help` for the list.

| Step                                               | Manual                            | `make`                                      |
| -------------------------------------------------- | --------------------------------- | --------------------------------------------- |
| Regenerate `plugins/` from `src/plugins/`          | (the sync block at the bottom)    | `make sync`                                 |
| Build the `.zip`s for claude.ai upload            | `zip -r …` per skill           | `make dist`                                 |
| Install skills for Claude Code                     | `cp -R … .claude/skills`       | `make install-claude-code`                  |
| Install runner deps                                | `pip install -r …`             | `make orchestrator-setup`                   |
| Provision the hosted agent                         | `python provision_agent.py`     | `make provision`                            |
| Run the pipeline (Agent SDK)                       | `python run_pipeline_sdk.py …` | `make run-sdk PACKET=path/to/packet.md`     |
| Run the pipeline (Managed Agents)                  | `python run_pipeline.py …`     | `make run-managed PACKET=path/to/packet.md` |
| Check plugins and skills are valid                 | —                                | `make verify`                               |
| Unit-test the sync/verify tooling                  | —                                | `make test`                                 |
| Remove build outputs                               | —                                | `make clean`                                |

The manual steps per method are spelled out below; use them, or the `make` equivalent — they do the
same thing.

## Method 1 — Claude Code  *(local, full capability)*

**Prerequisites:** Claude Code installed and logged in; this repo on disk.

1. **Install the plugin** so Claude Code discovers the skills (recommended — this is how users get
   updates):

   ```
   /plugin marketplace add IntuitioLabsLLC/rightshift-managed-agents
   /plugin install rs-scoping@rightshift
   ```

   *(To install every generated skill locally from this checkout instead, run
   `make install-claude-code`, which copies `plugins/*/skills/*` into `.claude/skills/`. For all your
   projects instead of just this one, copy them to `~/.claude/skills/`.)*
2. **Connect Notion (optional but recommended):**

   ```bash
   claude mcp add --transport http notion https://mcp.notion.com/mcp
   ```

   Then run `/mcp` inside Claude Code and complete the Notion OAuth login.
3. **(Optional) Install D2** so diagrams render to images:

   ```bash
   curl -fsSL https://d2lang.com/install.sh | sh -s --
   ```
4. **Verify** — start Claude Code in the repo and run:

   ```
   /brd-generator
   ```

   It should load and ask for the Opportunity Packet. Repeat for `/prd-generator`,
   `/technical-design-generator`, `/estimation-generator`.
5. **Run a single stage:** paste the Opportunity Packet and let the skill run its gated phases.
6. **Run the whole pipeline (orchestrated):**

   ```bash
   make install-claude-code                      # from the repo root: let the SDK runner find the skills (one-time)
   cd src/orchestrator
   pip install -r requirements.txt
   python run_pipeline_sdk.py --packet ../../path/to/opportunity-packet.md
   ```

   It runs BRD → PRD → Technical Design → Estimation, pausing at each human gate; artifacts land in
   `src/orchestrator/runs/`.

## Method 2 — claude.ai  *(web / desktop app)*

**Prerequisites:** a **Pro, Max, Team, or Enterprise** plan with **code execution enabled**
(Settings → Capabilities — skills don't appear without it).

> **GitHub is the source of truth, not a deploy channel.** claude.ai has no GitHub-sync for skills
> (its GitHub integration is repo *content* only) and no CLI to push skills to the web app. Every
> deploy is: commit → `make sync && make dist` → upload the changed zip(s).

1. **Package each skill as a zip** (the uploader takes one skill folder at a time — the skill folder
   must sit at the zip root with `SKILL.md` inside it, which is exactly what `make dist` produces):

   ```bash
   make dist          # or manually:
   mkdir -p dist
   (cd plugins/rs-scoping/skills && zip -r ../../../dist/brd-generator.zip               brd-generator)
   (cd plugins/rs-scoping/skills && zip -r ../../../dist/prd-generator.zip               prd-generator)
   (cd plugins/rs-scoping/skills && zip -r ../../../dist/technical-design-generator.zip  technical-design-generator)
   (cd plugins/rs-scoping/skills && zip -r ../../../dist/estimation-generator.zip        estimation-generator)
   ```
2. **Upload the skills:** in claude.ai open **Settings → Customize → Skills**, choose **Upload
   skill**, and upload each `.zip` from `dist/`. Confirm each shows as enabled. Note the skill
   `description` limit here is **200 characters** (the SKILL.md frontmatter descriptions are kept
   within it; the richer when-to-use text lives in each SKILL.md body).
3. **Distribute org-wide (Team/Enterprise):** a workspace **admin** can provision skills for the
   whole organization — upload once via the admin skill settings and every teammate gets them
   enabled by default (each user can toggle them off individually). Recommended flow: test the zips
   on your own account first, then hand them to the admin. Only Pro/Max users need per-user uploads.
4. **Connect Notion:** **Settings → Connectors → Notion → Connect**, and complete the OAuth login.
   This lets the skills read the Opportunity Packet and write outputs back to Notion.
5. **Verify:** start a new chat and type `/brd-generator` (or just ask "create a BRD from this
   packet…"). The skill should trigger.
6. **Run a stage:** paste or @-reference the Opportunity Packet; approve at each gate. For estimation,
   the skill fills the `.xlsx` in the sandbox (openpyxl is pre-installed), runs
   `scripts/validate_estimate.py` on it, and offers the workbook for download.

**Limitations to expect:** D2 diagrams come out as `.d2` source / SVG (no `d2` binary here); chaining
stages is manual (paste each output into the next) — use Method 1 or 3 for automatic chaining.

## Method 3 — platform.claude.com  *(Managed Agents — hosted, BETA)*

**Prerequisites:** an Anthropic API key; access to the Managed Agents + Files beta; `python3`.
This is the only path that produces one hosted agent running the full chain.

> Reminder: there is **no YAML agent file** to upload here — you upload the **skills**, then create the
> agent via the API. `pipeline.yaml` is the runner's config.

1. **Set up the environment:**

   ```bash
   cd src/orchestrator
   pip install -r requirements.txt
   export ANTHROPIC_API_KEY=sk-ant-...
   ```
2. **Upload each skill to your workspace and copy its `skill_id`.** Use the Console **Skills** page
   (Upload skill → pick the skill folder or its zip from `dist/`), or the Skills API / `ant` CLI.
   Each upload returns an id like `skill_abc123`.
3. **Map the ids** into `src/orchestrator/pipeline.yaml` under `platform.skills`:

   ```yaml
   platform:
     skills:
       brd-generator: "skill_abc123"
       prd-generator: "skill_def456"
       technical-design-generator: "skill_ghi789"
       estimation-generator: "skill_jkl012"
   ```
4. **Create the Notion credential vault** (OAuth) and put its id in `pipeline.yaml → notion.vault_id`:

   ```bash
   ant beta:vaults create --name notion-auth \
     --credential '{type: mcp_oauth, mcp_server_url: "https://mcp.notion.com/mcp", oauth_code: "...", oauth_redirect_uri: "https://..."}'
   ```

   *(Exact vault command/flags evolve — confirm on the MCP-connector docs; copy the returned `vault_*` id.)*
5. **Provision the agent + environment:**

   ```bash
   python provision_agent.py
   ```

   This creates one agent holding all four skills + the Notion MCP, plus a cloud environment, and
   writes their ids to `src/orchestrator/runs/agent.ids.json`.
6. **Run the pipeline:**

   ```bash
   python run_pipeline.py --packet ../../path/to/opportunity-packet.md
   ```

   It opens a session, runs the four stages (pausing at each gate), and downloads the filled
   `estimation.xlsx` to `src/orchestrator/runs/`.
7. **Verify:** check the run in the Console's agent/session view; confirm `runs/estimation.xlsx`
   exists and opens with computed totals.

**Beta notes (verify before production):** all Managed Agents calls need the
`anthropic-beta: managed-agents-2026-04-01` header and Files calls need `files-api-2025-04-14` (both
already wired from `pipeline.yaml`). Confirm the current header values, the `client.beta.*` resource
names, the `agent_toolset_20260401` tool string, and the session event types against the live docs.

## Method 4 — Agent SDK runner  *(pipeline in your own process / server)*

Same code as Method 1, step 6, but run anywhere with Python (a server, a cron job, CI). No hosted
beta, no skill upload — it executes the local skills.

1. ```bash
   make install-claude-code    # from the repo root, so the local skills are discoverable
   cd src/orchestrator && pip install -r requirements.txt
   export ANTHROPIC_API_KEY=sk-ant-...
   ```
2. ```bash
   python run_pipeline_sdk.py --packet ../../path/to/opportunity-packet.md
   ```
3. To trigger it from Notion or a button, wrap step 2 in your own endpoint and pass the packet path
   or Notion URL.

## After any method — keeping the skills current

Each skill's `resources/` are copies of the canonical prompts under `src/plugins/<plugin>/prompts/`
and `src/standards/`, declared in the plugin's `sync.json`. When you edit a canonical prompt,
re-sync and re-deploy:

```bash
make sync                 # regenerate plugins/ from src/plugins/ (+ standards, templates, context pack)
make dist                 # then rebuild the zips (Method 2), or
make install-claude-code  # re-install for Claude Code (Method 1, local copy)
```

When you promote a new prompt version, update the matching entry in that plugin's `sync.json` and
re-run `make sync`. For plugin users the change only reaches them through a release; see below.

## Updating a skill

The rule that catches people out: an update ships the **whole plugin**, never one skill, and
**nothing reaches anyone unless the version number changes.** Editing and pushing is not enough.

1. **Edit under `src/plugins/<plugin>/`.** Never in `plugins/` — `make sync` overwrites it. For
   prompt-backed skills, promote into `prompts/<stage>/current/`; the old version stays in `versions/`.
2. **`make verify`.** Catches a missing `name` or `description`, a bad manifest, an empty plugin.
3. **`make sync`.** Refuses to run if `plugins/` has uncommitted edits (the guard against hand-editing).
4. **Commit with a Conventional Commit type:** `prompt:` for a prompt or skill change, `feat:` for a
   new skill or plugin, `fix:` for a correction. The type drives the version bump and the changelog.
   (commitlint accepts `prompt` in addition to the standard types.)
5. **Release:** `npm run release`. commit-and-tag-version bumps `package.json`, every `plugin.json` and
   `marketplace.json`. Skipping this is how a change fails to reach anyone.
6. **Push, with tags:** `git push --follow-tags`.

### The version pin

Each `plugin.json` pins an explicit `version`, so users get nothing until that string changes.
Omitting `version` would make Claude Code derive it from the commit SHA, and every push would
propagate. We keep the pin for deliberate releases and a meaningful changelog, which makes step 5
mandatory. Example: a skill added without a version bump never reached anyone who already had the
plugin installed.

### How updates reach people

**Automatic**, where the marketplace has auto-update on (a user enables it under **Marketplaces** in
`/plugin`): after the user's first message in a session, Claude Code waits up to ten minutes, then
refreshes and updates the plugin on disk. The running session keeps the old version and shows
`Plugin updated: <name> · Run /reload-plugins to apply`. It loads on next launch either way.

**Manual:**

| Where | Command |
|---|---|
| In a session | `/plugin marketplace update rightshift` |
| In a session, one plugin | `/plugin install <plugin>@rightshift --upgrade` |
| From a shell | `claude plugin update <plugin>@rightshift` |

### Checking the catalogue

| Question | How to answer it |
|---|---|
| What plugins exist? | `/plugin` in a session, or read `.claude-plugin/marketplace.json` |
| What skills are in a plugin? | List `plugins/<name>/skills/` — skills are auto-discovered from there |
| What do I have installed? | `/plugin`, or `claude plugin list` |
| What version am I running? | `claude plugin list`, or the `version` in the installed `plugin.json` |
| What changed between versions? | `CHANGELOG.md` at the repo root, generated from Conventional Commits |
| Is my copy current? | `/plugin marketplace update rightshift` |

### Pending prompts

Stub and idea-stage prompts that are not yet skills are listed in each plugin's
`src/plugins/<plugin>/prompts/PENDING.md` (`rs-sales`, `rs-content`, `rs-project-management`). They
are not shipped as skills until the prompt body exists.

## Migrating from the old plugins

The old plugins `rightshift-doc-gen`, `chatbot-forge` and `delivery-agent` no longer exist. The
marketplace carries a top-level `renames` map so Claude Code migrates existing installs, per
[Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace#migrate-users-with-a-renames-map)
(requires Claude Code v2.1.193 or later):

| Old name | Renamed to |
|---|---|
| `rightshift-doc-gen` | `rs-scoping` |
| `chatbot-forge` | `rs-chatbot` |
| `delivery-agent` | `rs-delivery` |

`renames` maps one old name to **one** new name. `rightshift-doc-gen` was split across several
plugins, so after the rename you must install the others you need by hand. `rs-common` is pulled in
automatically as a dependency of `rs-scoping`; `rs-qa`
(and `rs-research`, `rs-sales`, `rs-content`, `rs-design`, `rs-prototype`, `rs-project-management`,
`rs-product`) have no old name to migrate from and still need a manual install.

For a marketplace added from a git repository, a renamed plugin reports `Plugin "<name>" not cached`
until the user installs the new name once:

```
/plugin marketplace update rightshift
/plugin install rs-scoping@rightshift
/plugin install rs-delivery@rightshift
/plugin install rs-chatbot@rightshift
/plugin install rs-qa@rightshift
```

If a rename does not apply (older Claude Code, or a managed `enabledPlugins` entry), uninstall the old
name and install the successors by hand:

```
/plugin uninstall rightshift-doc-gen@rightshift
/plugin install rs-scoping@rightshift
```

Managed settings are not rewritten automatically: an admin must update `enabledPlugins` there.

Marketplaces added without a ref track the default branch, so they see the new plugins and renames as soon as this lands on `main`; cut the release (3.0.0 and the `v3` tag) immediately after the merge.
